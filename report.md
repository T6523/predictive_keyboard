# Report: KenLM Pipeline — Architecture, Experiments, Results

Run reference: `weights/run_20260905_103654/` (production models, still current).

## 0. Methodology

Every change below follows the same loop:

1. **Isolate one variable at a time** on Model A alone (`train.src.tok`, 703MB, fast turnaround)
   — never touch Model B (`gigaword.tok`, 7GB, ~20min `build_binary` alone) until a hypothesis
   is proven on A first.
2. **Scratch dir per experiment** (`weights/experiments/exp_<name>/`), never overwrite the
   production run (`weights/run_20260905_103654/`).
3. **Compare against the last confirmed baseline** (stated at the top of each experiment section
   below), not against a moving target.
4. **Delete the scratch dir after recording the result** — the numbers in this report are the
   permanent record, the multi-hundred-MB/GB binaries are not.
5. **Only promote a change to production** (or to the shared toolchain, e.g. `scripts/bin/`)
   once it's validated on Model A and, where relevant, confirmed to still hold after
   interpolation — §3f's order-7 KenLM rebuild is the one exception that touched shared
   toolchain directly (see below), because it was a compile-time capability gate, not a modeling
   choice to A/B test.
6. **RAM-capped, backgrounded, monitored** — every `lmplz`/`build_binary` run passes an explicit
   `-S` memory cap sized against `free -h` headroom at launch time, runs via `nohup ... & disown`,
   and is polled to completion/failure rather than blocking the session.

## 1. Architecture (Part 1)

`ngram/pipeline.py` — deterministic training + inference pipeline.

- **Model A**: 5-gram KenLM, trained on `data/train.src.tok` (raw, unclean — punctuation/number
  tokens kept, lowercased, ~703MB).
- **Model B**: 5-gram KenLM, trained on `data/gigaword.tok` (raw, vocab-masked to Model A's
  vocab via `[UNK]`, ~7GB).
- Training: `lmplz -o 5 -S 12G --prune 0 0 1 --discount_fallback` → ARPA → `build_binary trie`
  → `.klm` (memory-mapped trie), ARPA deleted after compile.
- Inference: streams `data/devv_eval.csv` / `data/devv_test.csv` row-by-row (`csv.DictReader`),
  scores `context` column with both models' `.score()`, writes `model_a_logprob10` /
  `model_b_logprob10` columns. RAM stays flat (mmap + streaming, no full-file load).
- Reproducible: `lmplz` has no thread/seed nondeterminism in this build; same corpus bytes +
  same flags → byte-identical ARPA → byte-identical trie → identical scores, every run.
- Output: `weights/run_<timestamp>/{model_a.klm, model_b.klm, devv_eval_predictions.csv,
  devv_test_predictions.csv}`.

Production run: `weights/run_20260905_103654/` — `model_a.klm` 483MB, `model_b.klm` 4.37GB.

## 2. Next-word accuracy eval (`ngram/predict_accuracy.py`)

Separate task from Part 1's log-prob scoring: given `context` + `first letter`, predict the
exact next word, compare to `answer` column. Two routes:

- **Symbol route**: first letter non-alnum → deterministic rule (`scripts/symbol_predict.py`):
  `[` → `[UNK]`, anything else → itself. Pre-existing repo utility, verified ~100% on this data.
- **Alnum route**: first letter alnum → KenLM n-gram lookup. Candidate pool = `weights/vocab.txt`
  (98,993 alnum words, built from alnum-only corpus by `scripts/build_vocab.py`), filtered by
  first letter, ranked via `model.BaseFullScore(state, word, out)`: sort by `(ngram_length desc,
  log_prob desc)` — deepest actually-observed n-gram order wins, smoothed log-prob only breaks
  ties within the same order. Chosen over plain `BaseScore` argmax because Kneser-Ney smoothing
  can rank a common word above the true highest-count continuation for exact-match purposes.

## 3. Experiments and results

### 3a. Ranking logic: `BaseScore` argmax vs `ngram_length`-first (model_a, model_b, both splits)

| | BaseScore argmax (v1) | ngram_length-first (v2) |
|---|---|---|
| model_a eval | 51.61% | 51.42% |
| model_a test | 51.52% | 51.30% |
| model_b eval | 46.59% | 46.49% |
| model_b test | 46.78% | 46.67% |

**Result: no meaningful difference (~0.1-0.3pp).** KenLM's internal backoff already orders
candidates similarly to an order-first scheme in practice. Not the cause of the accuracy gap
vs. the prior pure-Python baseline (~55%).

### 3b. Corpus/pruning hypotheses (model_a only, eval split, isolated one-variable-at-a-time)

Baseline for comparison: model_a eval, old code (no symbol fix), 51.42%.

| experiment | change | corpus | accuracy | delta |
|---|---|---|---|---|
| no pruning | `--prune 0 0 0` instead of `0 0 1` | raw `train.src.tok` | 51.71% | +0.29pp |
| alnum-cleaned | same prune, corpus stripped to alnum-only | `clean/train.src.tok` | 45.19% | **-6.23pp** |

**Pruning hypothesis: dead.** Keeping singleton 3/4/5-grams barely moves accuracy — KenLM's
backoff already recovers most of what pruning would have removed via lower-order fallback.

**Cleaned-corpus hypothesis: dead, and actively harmful.** `devv_eval.csv` context strings
still contain punctuation tokens (~9% token density, matching raw corpus's ~11% — confirmed by
direct token count). A model trained on punctuation-stripped text treats every punctuation
token in the eval context as OOV, corrupting the KenLM state used to prime prediction. Training
vocabulary must match eval context format; the raw/unclean corpus is the *correct* choice for
Part 1, not a bug.

### 3c. Symbol-route wiring (the actual fix)

`ngram/predict_accuracy.py` originally never called `symbol_predict.py` — symbol-letter rows (~10.7%
of every split, 8148/75860 eval, 2037/18965 test) fell through the alnum candidate lookup,
found nothing, and were silently scored wrong. Wiring in `is_symbol_letter`/`predict_symbol`
before the alnum branch fixed this.

| model | split | overall (before) | overall (after) | alnum-only | symbol-only |
|---|---|---|---|---|---|
| model_a | eval | 51.42% | 62.10% | **57.61%** | 99.37% |
| model_a | test | 51.30% | 61.98% | **57.47%** | 99.41% |
| model_b | eval | 46.49% | 57.16% | **52.08%** | 99.37% |
| model_b | test | 46.67% | 57.35% | **52.29%** | 99.41% |

**This was the real gap.** ~10.7pp of overall accuracy was purely a missing deterministic rule,
unrelated to the KenLM model or ranking logic. Model A's true (alnum-only) accuracy, 57.6%,
now exceeds the prior pure-Python baseline (~55%).

### 3d. Part 2: interpolation of Model A + Model B (log-prob / perplexity)

`ngram/interpolate.py`. Standard linear interpolation in probability space: `P = λ·10^logA +
(1-λ)·10^logB`, perplexity `= 10^(-Σlog10(P)/word_count)`. Reuses `model_a_logprob10` /
`model_b_logprob10` columns already written by `ngram/pipeline.py` — no rescoring, pure CSV
arithmetic. λ tuned by grid search (step 0.01) minimizing perplexity on `devv_eval`, then
applied as-is to `devv_test`.

| | eval perplexity | test perplexity |
|---|---|---|
| model A alone (λ=1) | 92.337 | 92.214 |
| model B alone (λ=0) | 150.597 | 150.503 |
| **interpolated (λ=0.71)** | **73.956** | **74.000** |

Best λ (0.71, tuned on eval) generalizes cleanly to test (73.956 → 74.000, no overfitting).
Interpolation beats both solo models on both splits — ~20% perplexity reduction vs. Model A
alone. Confirms Model A (in-domain) and Model B (gigaword) carry complementary information
worth combining, even though A dominates the mixture weight.

### 3e. Interpolation applied to next-word accuracy

`predict_accuracy.py --model-b ... --lam 0.71` (new `predict_interp`): per candidate, prime a
separate context state per model, argmax over `λ·10^logA + (1-λ)·10^logB` (probability-space
interpolation, same formula as `ngram/interpolate.py`, applied per-candidate instead of per-sentence).
Reused the perplexity-tuned λ=0.71 as-is, no separate accuracy-specific tuning yet. Symbol
route unaffected (deterministic rule, no model involved).

| | eval alnum-only | test alnum-only |
|---|---|---|
| model A solo | 57.61% | 57.47% |
| model B solo | 52.08% | 52.29% |
| **interpolated (λ=0.71)** | **60.16%** | **60.02%** |

+2.5-2.6pp over Model A alone, consistent across both splits, no overfitting (eval and test
track each other closely, same as the perplexity result). Confirms the perplexity-domain
interpolation gain transfers to the accuracy objective even without re-tuning λ specifically
for it.

**Not yet done:** grid-searching a separate accuracy-tuned λ (current 0.71 was tuned for
perplexity, not accuracy — a different optimum may do slightly better, at the cost of one
`ngram/predict_accuracy.py` pass per grid point, ~2800s eval / ~220s test each).

### 3f. Higher n-gram order (`--prune 0 0 1` unchanged, isolated, solo model — no interpolation)

Baseline: model_a alone, order 5, alnum-only — 57.61% eval / 57.47% test.

| order | model_a eval | model_a test | model_b eval | model_b test |
|---|---|---|---|---|
| 4 | 57.00% | 56.73% | 51.05% | 51.11% |
| 5 | 57.61% | 57.47% | 52.08% | 52.29% |
| 6 | 57.74% | 57.81% | not tested (7GB corpus, hours/run — deferred) |
| 7 | **57.81%** | **57.86%** | not tested (7GB corpus, hours/run — deferred) |

Both models improve monotonically with order and both flatten out, but at different rates:
model_a's curve is nearly plateaued (4→5 +0.6pp, 5→6 +0.13pp, 6→7 +0.07pp); model_b's 4→5 jump
is bigger (+1.0pp eval, +1.2pp test) — consistent with a ~10x larger corpus still having headroom
at low orders that model_a's smaller corpus has already used up. model_b order-6/7 were
deliberately not run (§0 methodology + explicit user call): each is a multi-hour, heavy-RAM job
on the 7GB corpus, only worth it once combined with interpolation shows the gain is real
end-to-end, not just on model_b solo.

**Order-6: negligible gain, not worth it standalone.** +0.1-0.3pp for a bigger/slower model — same
pattern as §3a/§3b, KenLM's backoff already captures most of what deeper context would add.

**Order-7 update:** user asked for max accuracy, requested order-7 be tried properly. KenLM's
stock build caps at `KENLM_MAX_ORDER=6` (native `build_binary` *and* the pip `kenlm` bindings both
enforce this at load time) — rebuilt both from source with `-DKENLM_MAX_ORDER=9` /
`MAX_ORDER=9 pip install`, verified backward-compatible with existing order-5/6 models via a smoke
test, then promoted into `scripts/bin/`. Order-7 ran clean: **57.81% eval / 57.86% test alnum**,
+0.07pp / +0.05pp over order-6 — monotonic but shrinking gains, classic diminishing-returns curve.
Not worth pushing to order-8/9. `scripts/bin/{lmplz,build_binary}` now support up to order-9 going
forward (backward compatible, no behavior change for order ≤6). Scratch dirs (`exp_order6` 639MB,
`exp_order7` 808MB) deleted after comparison.

### 3g. Order-aware interpolation (per-candidate deepest-order wins, no fixed λ)

`predict_accuracy.py --order-aware` (new `predict_order_aware` / `_order_aware_key`): per
candidate, compute `BaseFullScore` on both models, take `max((ngram_length_a, log_a),
(ngram_length_b, log_b))` — whichever model matched the deeper n-gram order wins outright,
log-prob only breaks a tie at equal order. No λ, no probability blending. Idea was that a
fixed-λ blend always weights Model B's spurious deep-but-shallow-domain matches the same amount,
while order-aware would let genuinely deeper context win regardless of source model.

| | eval alnum | test alnum |
|---|---|---|
| λ=0.71 interpolation (§3e, baseline) | **60.16%** | **60.02%** |
| order-aware | 59.63% | 59.49% |

**Hypothesis disproven — order-aware is worse, by -0.53pp both splits (consistent, not noise).**
Likely cause: n-gram order isn't a reliable cross-model quality signal the way it is within one
model. Model B (gigaword, out-of-domain) can match a deep order on a generic phrase with weak
actual probability mass, and order-aware blindly prefers that over Model A's shallower but
confident smoothed estimate — probability-space blending (λ) naturally weighs by actual mass,
strict order-first doesn't. Consistent with §3a's finding that order-first ranking barely helps
even within a single model. Scratch dir deleted after comparison (16KB, logs only).

### 3h. Number-masking bug in Model B's corpus (found and fixed)

User suspicion, verified by trace: `train.src.tok` (Model A) masks every literal number to a
same-length run of `1`s (`15`→`11`, `2020`→`1111`, capped at 8 digits — `weights/vocab.txt` has
exactly 8 number entries). `scripts/tokenize_gigaword.py` (Model B's corpus builder) never did
this — it only checked vocab membership, and since the vocab has no literal digit strings, every
real number in the raw gigaword text (`"15-inch"`, `"June 12"`, ...) fell through to `[UNK]`
instead of landing in the right repunit bucket. Confirmed on a 500MB sample: 0 literal
multi-digit numbers survived un-masked in the old file (all silently became `[UNK]`), pushing
that chunk's UNK rate to 4.52% vs 2.92% after the fix.

Fix: `mask_number()` — `"1" * len(tok) if tok.isdigit() else tok` — applied before the vocab
check in `tokenize_line()`. Re-tokenized the full 7GB corpus to `gigaword_maskfix.tok` (~30min),
verified full-file UNK rate 2.96% (down from an unmeasured but clearly higher rate — literal
numbers were a meaningful fraction of Model B's out-of-vocab mass), then promoted it to
`data/gigaword.tok` (original backed up as `gigaword.tok.premaskfix.bak`, not git-tracked but
kept on disk). Retrained model_b at order-5 (same flags: `-S 12G --prune 0 0 1
--discount_fallback`), old `model_b.klm` backed up as `model_b.klm.premaskfix.bak`.

| | eval alnum | test alnum |
|---|---|---|
| model_b solo, before fix | 52.08% | 52.29% |
| model_b solo, after fix | **52.91%** | **53.01%** |
| Δ | +0.83pp | +0.72pp |
| λ=0.71 interpolated, before fix | 60.16% | 60.02% |
| λ=0.71 interpolated, after fix | **60.29%** | **60.15%** |
| Δ | +0.13pp | +0.13pp |

Clean, real, consistent gain on model_b solo (~+0.8pp both splits — this was a genuine corpus
bug, not noise). Smaller effect once interpolated (+0.13pp) since λ=0.71 already weights Model A
(unaffected by this bug) more heavily — model_b's improvement gets diluted by its own 29% share
of the blend. This is now the production model_b; order-6/7 on model_b (deferred in §3f) should
be retried on this corrected corpus if pursued, not the old buggy one.

## 6. Cross-model comparison: from-scratch GPT2 transformer

A third approach, not a KenLM variant: `gpt/33k_full_gpt/` -- a 497M-param GPT2-medium-
widened model (`n_embd=1152, n_layer=24, n_head=18`, ~99k word-level vocab built straight from
`data/train.src.tok`, no subword/BPE), trained from random init (never pretrained), softmax
masked to the target's first-letter bucket at every training position, resumed across multiple
8hr Kaggle sessions to step 32513 (`gpt/kernel/build_notebook.py`).

Same next-word-accuracy task as §2 (`ngram/predict_accuracy.py`), same symbol-route rule
(`scripts/symbol_predict.py`), same eval files, evaluated by `gpt/33k_full_gpt/infer.py`
(local) / `gpt/infer_kernel/infer_kaggle.py` (Kaggle script-kernel copy, self-contained) via
masked argmax over the model's own logits (mirrors `build_notebook.py`'s `predict()` exactly, no
candidate-pool lookup needed -- the model's vocab head already covers every word).

| | overall | alnum-only | symbol-only |
|---|---|---|---|
| devv_eval | 70.87% | **67.44%** | 99.37% |
| devv_test | 71.45% | **68.09%** | 99.41% |

**Beats the best n-gram result (§4: 60.16%/60.02% alnum, λ=0.71 interpolated A+B) by
+7.3-8.1pp alnum accuracy.** Symbol route ties with the n-gram (deterministic rule either way,
same ~99.4% both places -- the ~0.6% miss rate is `scripts/symbol_predict.py`'s own ceiling
against this data, unrelated to which model handles the alnum route).

Predictions saved to `gpt/33k_full_gpt/devv_eval_predictions.csv` /
`devv_test_predictions.csv`, schema `context,first letter,answer,predicted,is_correct,
gpt_logprob10` -- the last column (log10 P(true answer | context) under this model) is what lets
`ensemble/ensemble_gpt_ngram.py` blend it with model_a/model_b's per-candidate KenLM scores without a
third rescoring pass.

Two things caught while running this, worth keeping in mind for future kernels:

- **Checkpoint identity, not just file size.** A stale intermediate checkpoint (step 25972, an
  earlier resume-session save) was first assumed identical to the final one (step 32513) purely
  because both `.pt` files were the same byte size -- true but meaningless, since checkpoint size
  is fixed by param count, not training step. Caught from the kernel's own startup print
  (`loaded gpt2 @ step N`), not from anything about the file itself.
- **Script-kernel vs local speed.** Local inference (RTX 4060, 8GB) stalled at <1.5 rows/s
  (CPU-bound at ~98% single-core despite the GPU also pegged -- cause unconfirmed, likely per-row
  Python/kernel-launch overhead rather than a compute limit). The same workload on Kaggle's T4
  finished both files in ~28 minutes total. Moved the task to a Kaggle script kernel rather than
  debugging the local stall further.

## 7. Cross-model comparison: Qwen2.5-0.5B LoRA fine-tune

A fourth approach: LoRA fine-tuning a pretrained subword LLM (`unsloth/Qwen2.5-0.5B`) instead of
training word-level from scratch. `qwen/train_and_eval.py` -- r=16, alpha=32, dropout=0, all 7
attention/MLP projections (`q/k/v/o_proj`, `gate/up/down_proj`), trained on the same raw
`data/train.src.tok`, hard-stopped at an 8h Kaggle-session budget (`TimeBudgetCallback`),
effective batch size 16 (`per_device=4 x grad_accum=4`), lr=2e-5 cosine schedule, warmup 3%.

Same next-word-accuracy task as §2/§6, same symbol-route rule, same eval files, evaluated by
`qwen/eval_kernel/eval_qwen.py` (Kaggle script kernel, separate from training -- the training
run's own in-line eval pass OOM'd, see below) via a KV-cache batched teacher-forced scoring loop
over the candidate pool, restricted first by a cheap KenLM (model_a) shortlist (top 80 candidates
by 5-gram score, measured 94.95% recall of the true answer on a 500-row sample -- caps achievable
accuracy at that ceiling regardless of what Qwen does with the remaining 5%, see below).

Getting the eval pass working correctly cost real engineering, worth recording because these are
easy bugs to reintroduce: (1) `DynamicCache.batch_repeat_interleave(n)` mutates in place and
returns `None` -- reassigning its return value silently drops the whole cache; (2) the original
scoring code was off by one logit position (`logits_to_keep=L` keeps the model's *last* L rows,
which predict tokens L+1..2L past the context, not 1..L); (3) `FastLanguageModel.for_inference()`
patches Qwen's forward to route any `past_key_values`-bearing call through unsloth's own
single-token `generate()` decode path, which hard-asserts `q_len == 1` and can't accept a
multi-token candidate batch -- confirmed against unsloth's own GitHub issues (#497, unresolved)
before fixing by skipping unsloth's inference path entirely (`merge_and_unload()` the LoRA into
plain `transformers` weights); (4) `peft`'s LoRA adapter dispatcher eagerly version-checks
`torchao` even for adapters that never touch it, breaking on Kaggle's older preinstalled version.
Full detail (tracebacks, fixes) lives in `qwen/eval_kernel/eval_qwen.py`'s module docstring.

| | overall | alnum-only | symbol-only |
|---|---|---|---|
| devv_eval | 46.22% | **39.83%** | 99.37% |
| devv_test | 45.74% | **39.28%** | 99.41% |

**Loses to every other approach tried** -- -20.5pp alnum vs. the best n-gram (§4: 60.29%/60.15%),
-27.6pp vs. the from-scratch GPT2 (§6: 67.44%/68.09%). Symbol route ties everyone else as usual
(deterministic rule, model-independent).

**Root cause: the LoRA adapter is badly undertrained, not a scoring bug.** The training run's own
log shows the 8h hard stop landing at step 7290, **epoch 0.767** -- three-quarters of a single
pass over the 3.8M-line / ~128M-word training corpus -- with the loss still actively falling
(~2.53-2.59, no plateau) and the cosine LR schedule barely decayed (1.75e-05 of a 2e-05 peak,
since the schedule's step budget assumed a full epoch that was never reached). See
`qwen/output/8hr/loss_curve.png`. A handful of manually inspected wrong predictions confirm this
reads as undertraining rather than a residual bug: the errors are fluent, plausible completions
in the *wrong style* for this corpus (`kilometers`→`km`, `tonnes`→`tons`, `internationals`→
`international`, `united`→`uae`) -- pretrained Qwen's general-web priors are still doing most of
the talking; three-quarters of one epoch of r=16 LoRA wasn't enough to override them toward this
corpus's specific word choices the way the n-gram (sees the whole corpus directly) and the
from-scratch GPT2 (many more steps, trained on nothing else) both did. The shortlist ceiling
(94.95% recall @ K=80) explains at most ~5pp of the gap, not the other ~15-20pp.

Not yet done: a longer or resumed training run (`train_and_eval.py` has no resume-from-adapter
support yet, see its own module docstring) to see whether accuracy actually improves once the
adapter converges, before concluding LoRA fine-tuning at this scale is a dead end here.

## 8. 3-way ensemble: Model A + Model B + GPT2 (proxy)

`ensemble/interpolate_gpt.py` -- same idea as §3d's Model A + B interpolation, extended to 3 models and
retargeted at the true-answer's probability (next-word setting) instead of whole-sentence
perplexity. Alnum rows only (67712 eval / 16928 test). log10 P(true answer | context) blended
in probability space (`P = w_a·10^logA + w_b·10^logB + w_gpt·10^logGPT`), weights grid-searched
(step 0.05) minimizing eval perplexity, applied as-is to test.

**This is a fast proxy, not blended top-1 accuracy** -- it measures likelihood mass on the
truth, which correlates with but isn't the same as whether the blended argmax actually picks
the right word. `ensemble/ensemble_gpt_ngram.py` computes the real accuracy-space version (grid search
over per-candidate blended argmax, same task as §2/§3e) but needs a fresh KenLM score for every
same-first-letter candidate under both n-gram models plus a GPT forward pass, per row -- a true
rescoring pass, not arithmetic over existing columns, so it costs ~5.6hr projected for the full
eval+test set (~4x §3e's already-noted 2-model interpolation cost) vs. this proxy's ~53s. Not
yet run to completion; queued as future work below.

| | eval perplexity | test perplexity |
|---|---|---|
| model A alone | 1.178 | 1.178 |
| model B alone | 1.212 | 1.213 |
| GPT2 alone | **1.147** | **1.147** |
| **interpolated (a=0.20, b=0.10, gpt=0.70)** | **1.137** | **1.137** |

GPT2 alone already beats both n-grams on this metric (expected, given §6's much higher alnum
accuracy). Blending in a modest amount of both n-grams (30% combined weight) still helps a little
further (1.147 → 1.137, ~0.9% perplexity reduction), and the weights tuned on eval reproduce
almost exactly on test (1.137 both splits) -- no overfitting. Confirms the n-grams carry some
information GPT2 doesn't fully capture, even though GPT2 dominates the mixture, same qualitative
pattern as §3d's Model A + B result (worth combining, even if one member dominates the weight).

## 9. Ideas not yet tried (future work)

1. **Combine order-7 with interpolation** — §3e's λ=0.71 interpolation used order-5 for both
   models; §3f's order-7 gain was measured on Model A solo. Retraining Model A at order-7 (or 6)
   and re-running `predict_interp` against Model B (still order-5) would show whether the two
   gains stack, before deciding whether Model B is worth retraining at a higher order too.
2. ~~Order-aware interpolation of Model A + B~~ — done, §3g. **Worse** than fixed λ=0.71
   (-0.53pp both splits). Cross-model order isn't a reliable quality signal; λ=0.71 stays best.
3. **Roll higher order to Model B, redo interpolation** — Model B is ~10x bigger (7GB corpus),
   so retraining it at order-6/7 is the expensive step; worth it only after (1) above shows the
   combined gain justifies it.
4. **Accuracy-tuned λ grid search** — current λ=0.71 was tuned for perplexity (§3d), not
   accuracy; a separate grid search directly against alnum accuracy on `devv_eval` (§3e) may do
   slightly better. ~2800s per grid point on eval, so a coarse grid (step 0.05) first.
5. **True stupid-backoff scoring** (`0.4^k` discount per order, matching `eval_ngram.py`'s
   convention) instead of `ngram_length`-first tie-break — closer to the pure-count baseline's
   exact formula.
6. **Run `ensemble/ensemble_gpt_ngram.py` to completion** — §8's proxy says a small gain is plausible
   (1.147 → 1.137 perplexity); the real blended-argmax accuracy number needs the full ~5.6hr
   rescoring pass (background job, not yet run to completion).
